How LyraCore divides world work and scales forward

The Discord proposal has two ideas. It activates only the world near players. It also gives separate areas to worker threads. LyraCore uses the first idea now. At a larger scale, it assigns separate maps to separate SpacetimeDB shards. The same seams give us a measured path to more capacity.

Important: LyraCore divides work at two different scales. A shard owns a map or instance. Active cells reduce the work inside that shard.

Scale 1: the gateway routes maps to shards

A shard is one SpacetimeDB database. The gateway selects the shard when a player enters the world. A continent can run on one shard while another continent runs on a different shard.

Large areas are separate

Kalimdor work does not run in the Eastern Kingdoms database.

The gateway owns routing

Game reducers do not read shard names. This keeps the module relocatable.

Instances have their own scope

A busy dungeon can use its own tick schedule. This divides work, but it does not add worker threads inside one database.

Scale 2: active cells reduce work inside one map

Each world entity stores its map, instance, and cell. A player activates the cells that cover the visible area. Normal creatures outside all active areas stay dormant.

What one creature tick does

The tick is one ordered SpacetimeDB transaction. The order protects gameplay rules. The module does not lock cells or start worker threads.

1. Select scopeSelect the map instances for this firing.
2. Find playersUse each player position to build the active cell set.
3. Run active workTick normal creatures that players can observe.
4. Run required workContinue combat, movement, and due timers.
5. CommitSpacetimeDB applies all changes as one transaction.

How LyraCore can scale from here

One realm can use many gateway processes and many databases. Players still see one realm-list entry. We add capacity at the layer that reaches its safe limit.

Scaling rule: more gateways do not make one hot Kalimdor writer faster. More databases do not remove dense crowd fan-out. Measure the first limit, then change that layer.

Measure the current realm

Record safe capacity for dispersed players, dense crowds, login storms, combat, and transfers. Find the first saturated resource.

Scale the gateway edge

Reduce per-session threads. Bound output queues. Add realm-wide admission. Prove a fixed fleet behind one TCP load balancer.

Scale authoritative writes

Optimize hot reducers first. Add instance buckets or another database only when state has a clear owner and the benchmark shows a writer limit.

Revisit sub-map seams

Split one hot continent only if it stays saturated. Require stable routing, Escrow, cross-seam gameplay rules, and failure recovery.

LyraCore already avoids a full-continent gameplay tick. It routes maps and instances to separate database writers, then activates only the useful cells inside each map. Going forward, we can add gateways for edge capacity and add databases for measured authoritative hotspots. A sub-map seam remains available as a later option, not the first step.
