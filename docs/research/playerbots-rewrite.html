Spec
Rewrite playerbots around durable objectives and typed action outcomes

Problem statement

The current playerbots Package can accept an action without proving that the action completed, loses route results, treats attempted combat as quest progress, bypasses the normal cast lifecycle, and retains too little purpose across interruption, restart, and Transfer. Bots can therefore stall, repeat work, choose an obsolete target, or abandon useful intent without explaining why. The current tests also do not prove the Package and core together against real actor operations, imported content, navigation, protocol transitions, and sustained load.

Solution

Replace the behavior control flow with one typed Rust decision runner shared by autonomous bots and human-led companions. The runner observes bounded facts, composes supported Strategies, ranks target-bearing candidates deterministically, executes actions through core operations, records typed outcomes, and retains one durable objective with bounded failure memory. Build the rewrite through a pinned real Module and Package fixture, then prove companion behavior, provisioning, seeded quest loops, recovery, commands, restart, Transfer, load, cutover, and attended client behavior before deleting the displaced implementation.

User stories

  1. As an Operator, I want every bot controlled by one eligible runner, so that two behavior systems cannot issue conflicting actions.
  2. As an Operator, I want a stopped bot to report its objective, target, chosen action, outcome, retry count, next eligible time, and content revision, so that I can diagnose it without reading source.
  3. As an Operator, I want decision work scheduled in bounded fair batches, so that a large roster cannot monopolize a Module tick.
  4. As an Operator, I want excess due bots deferred with recorded lag, so that overload does not silently discard durable work.
  5. As an Operator, I want repeatable provisioning profiles, so that I can explain why a bot received a spell, item, or supply.
  6. As an Operator, I want deployment capacity based on measured runs of 10, 25, and 100 bots, so that release limits reflect this implementation.
  7. As a developer, I want fixed facts and time to produce the same decision, so that policy changes have reproducible tests.
  8. As a developer, I want candidates identified by action, target, and relevant event, so that a higher score cannot retain the wrong target.
  9. As a developer, I want each supported action to return a typed outcome, so that success, waiting, Refusal, cancellation, expiry, and infrastructure failure remain distinct.
  10. As a developer, I want action prerequisites, alternatives, and continuers to be bounded, so that retries and cycles cannot run forever.
  11. As a developer, I want a reproducible Module and Package fixture at pinned revisions, so that failures and fixes can be compared against the same content and geometry.
  12. As a developer, I want casts to use the normal core cast-start lifecycle, so that cast time, interruption, cancellation, cost, and completion use the same Gates as client casts.
  13. As a developer, I want movement outcomes to preserve route completion and coverage evidence, so that policy can distinguish progress, a partial route, blockage, and unknown coverage.
  14. As an autonomous bot, I want one objective retained across tactical interruptions, so that defending myself does not erase my quest purpose.
  15. As an autonomous bot, I want quest admission to require an executor for every required objective, so that unsupported quests do not trap me.
  16. As an autonomous bot, I want to accept, travel for, complete, and turn in a supported kill quest, so that I can earn normal quest credit and XP.
  17. As an autonomous bot, I want to find the actual drop source, loot it, and turn in a supported collect quest, so that collection progress comes from gameplay outcomes.
  18. As an autonomous bot, I want supported talk-only chains and simple GameObject objectives executed through normal core interactions, so that a quest route does not stop at a non-combat step.
  19. As an autonomous bot, I want the actual quest ender retained from the catalog, so that I travel to the correct turn-in Character or GameObject.
  20. As an autonomous bot, I want death, combat, full bags, absent targets, and temporary route failure to have finite recovery rules, so that I can resume or stop with a specific reason.
  21. As an autonomous bot, I want a failed destination deferred by map, instance, and geometry revision, so that a restart cannot immediately choose the same failed target again.
  22. As an autonomous bot, I want skill and spell training, vanilla talents, equipment, and supplies reconciled on spawn and level-up through core Gates, so that I remain playable without receiving invalid progress.
  23. As a human party leader, I want a companion to follow or stay on command, so that I control its position.
  24. As a human party leader, I want a companion to assist my chosen fight or a designated target, so that it does not pull an unrelated enemy.
  25. As a human party leader, I want companions to respect controlled enemies, so that crowd control is not broken by autonomous target choice.

  27. As an injured party member, I want a Priest companion to repair range or line of sight and complete one real heal cast, so that repeated decisions do not restart the cast bar.
  28. As a party member, I want a Warrior tank to hold the chosen fight and a Mage damage companion to act at class-appropriate range, so that role does not erase class capabilities.
  29. As a companion, I want joining a human-led party to suspend autonomous travel and leaving it to resume a still-valid solo objective, so that control changes preserve useful intent.
  30. As a companion, I want my role, party intent, and retained objective reconciled after restart and Transfer, so that delayed work from the old location cannot act.
  31. As a maintainer, I want the old behavior source and obsolete state retired after both release suites pass, so that one implementation remains authoritative.
  32. As a party member, I want companions to heal and apply useful missing buffs between fights, so that the party starts the next fight ready without repeated redundant casts.

Implementation decisions

  • Use a targeted Rust rewrite of the useful AzerothCore decision grammar. Do not port its C++ runtime, synthetic World Sessions, packet queues, host object graph, or WotLK rules.
  • Keep durable gameplay authority in the Module. Keep party authority in Realm-core. Use existing Transfer and Group Intent routing only for their realm-wide responsibilities.
  • Give the Package one small decision interface, one action execution interface, and one explanation read. Keep internal behavior behind those interfaces.
  • Represent Strategies, triggers, facts, candidates, actions, targets, outcomes, tactical modes, objective stages, and failure reasons with typed values instead of strings and dynamic lookup.
  • Rank candidates with integer scores and stable tie-breaking. Candidate identity includes the action, target, and relevant event. Saved random state may break equal valid choices only.
  • Support bounded prerequisites, alternatives, and continuers. Limit candidate count, graph depth, transitions, and route expansion independently during each decision pass.
  • Allow one foreground action to own movement or a cast. A higher-priority action must explicitly cancel incompatible work before it starts.
  • Retain the quest or party objective across tactical interruption. Store its identity, destination, stage, deadline, last verified progress, deferred destinations, bounded failure memory, and catalog revision.
  • Keep route segments and live target observations transient. Correlate pending work with controller generation and location so stale completions cannot advance current state.
  • Treat action acceptance and actual progress as different facts. Track movement, combat, cast, and quest progress with separate evidence and clocks.
  • Expose typed outcomes from the owning core operations for the actions the selected behaviors require. Preserve existing Gates and atomic Refusal behavior.
  • Route bot spells through the normal cast-start and timed completion lifecycle. A running cast stays retained until completion, interruption, cancellation, or expiry.
  • Preserve complete, partial, blocked, and explicit unknown-coverage movement evidence. Do not infer missing coverage only from absent sparse navigation rows.
  • Derive tactical mode and active Strategies from durable Character, party, combat, aura, health, threat, target, position, and capability facts. Do not create a second authoritative state machine.
  • Use the bounded priority order from the report: lifecycle and Transfer restrictions, immediate survival, urgent party support, the current fight, human orders, maintenance, autonomous quest work, then idle activity.
  • Store an indexed next-decision time per bot, process due bots in stable order with a fixed batch limit, coalesce urgent reconsideration reasons, and record lag for deferred work.
  • Build a versioned supported quest catalog from imported quest relations, objectives, spawns, loot sources, and actual enders. Admit only quests whose required objectives have executors.
  • Start autonomous release coverage with a seeded Northshire and Elwynn catalog and ordinary quest credit and earned XP. Treat this as a bounded proof rather than level 1 to 60 coverage.
  • Start companion release coverage with Warrior tank, Priest healer, and Mage damage capabilities. Store the explicit role and derive a deterministic vanilla default when none is chosen.
  • Support durable follow, stay, assist, and designated-target orders through the existing command transport. Joining a human-led party suspends solo work; leaving rechecks and resumes it when valid.
  • Reconcile skill and spell training, vanilla talent choices, equipment, bags, food, potions, ammo, reagents, and bounded supplies as separate idempotent actions through core Gates. Provisioning never changes level, grants quest completion, deletes quest items, or duplicates owned resources.
  • Add new state through an additive migration and one durable controller selector. Use record-only comparison before a small active cohort, then retire the old controller and its obsolete state after release acceptance.
  • Keep a bounded history of transitions and failures. Do not retain one row for each successful idle decision.

Testing decisions

  • Use the highest real seam available. Pure tests cover deterministic policy, durable Module and Package fixtures cover gameplay operations and navigation, Headless Client scenarios cover protocol and world transitions, and attended client observation covers visible behavior.
  • The baseline fixture pins core commit 95e6ad8c61540f74471e3087897e8c3ef7e065d1 and Package Collection commit c32b2fb7aa405190728034b63ce6eb9a3c0dd6be together with named imported content and geometry revisions.
  • Every supported action has behavioral cases for success, waiting, Refusal, cancellation, and expiry. Infrastructure failures remain separate where the seam can produce them.
  • Durable fixtures call real actor, cast, movement, quest, loot, item, and lifecycle operations. They do not replace gameplay with a simulated combat model.
  • Decision fixtures cover stable candidate order, target-bearing identity, bounded transition graphs, survival against role work, healing against following, and combat interruption against retained quest work.
  • Movement fixtures measure route or waypoint advancement. After 10 seconds without movement progress the bot changes approach; within 30 seconds it advances, defers the destination, or records a specific wait.
  • Cast fixtures prove one long cast starts once, survives intervening decisions, and ends once by completion, interruption, cancellation, or expiry.
  • Companion fixtures cover follow, stay, assist, designated target, controlled enemies, poor range, loss of line of sight, wounded allies and missing buffs between fights, death, regrouping, and one instance entry and exit.
  • Autonomous fixtures run ten seeds per starter class through the supported Northshire and Elwynn catalog. All ten runs per class must finish each supported scenario without Operator help: nine of ten is below the 95 percent requirement. Every failed run must record an explained outcome and fails the release gate.
  • Autonomous mandatory scenarios include kill, collect, talk-only chains, supported simple GameObject use, turn-in, death, interruption, full bags, absent targets, an unreachable giver, unsupported objectives, and restart with a retained objective.
  • Restart and Transfer fixtures interrupt active action and escrow stages. They prove no duplicate Character, equipment, supply grant, quest reward, or active controller and prove stale work cannot act on the old location.
  • Load fixtures run 10, 25, and 100 bots on one named disposable fixture and record decision time, movement time, scheduler lag, route expansions, row reads, row writes, and the slowest due bot before capacity is set.
  • Final observation requires one hour with 25 bots on imported content plus an attended companion session in a real unmodified 1.12.1 client. A human must collect and sign off this evidence if the implementation environment cannot run that client.
  • Review final behavior against this specification and repository standards after the focused and full relevant checks pass.

  • A user-defined action language, global string factory, client addon, or new product UI.

4. One owner decides, core operations act

The Package owns bot policy and a bot's durable objective. The Module owns all gameplay state and Gates. The Gateway continues to route Transfer and Group Intents. A new native process that keeps a second copy of bot decisions would add synchronization work before it solves the current behavior failures. Current authority.

Keep the external interface small

decide(facts, retained_state, now) -> decision
advance(ctx, character_guid, decision) -> action_outcome
explain(character_guid) -> current objective and recent decisions

These are proposed shapes, not new Package API commitments. The pure decision function receives bounded facts and explicit time. The executor calls real Module operations. Durable integration tests exercise both through the bot's normal entry point. There is no trait for every helper and no separate simulated combat model.

Allow one foreground action to own movement or an active cast at a time. Existing auto-attacks and core effect timers may continue. A lower-priority proposal cannot replace a running cast or route; a higher-priority interruption must cancel it explicitly. Starting a long cast and starting it again on the next tick is a failure, even if both calls return success.

Retain the objective; interrupt the action

A bot walking to turn in a quest should defend itself, heal, and then resume that turn-in. It should not discover a new quest because combat ended. Retain the quest and objective identity, chosen destination, stage, deadline, last verified progress, and deferred candidates. Keep path waypoints and live target observations separate so they can expire without erasing intent.

Use a bounded priority order: lifecycle and Transfer restrictions, immediate survival, urgent party support, the current fight, human orders, maintenance, autonomous quest work, then idle activity. A tank's survival policy may choose a defensive ability or local retreat. It should not inherit a damage bot's run-home action. Test each contested pair rather than rely on unexplained numeric scores.

Schedule decisions without repeated full work

The current pass scans the roster and makes each due bot think once a second. Start from the core-owned tick, then use an indexed due time, stable staggering, and a per-pass work limit. Hooks record an urgent reason to reconsider; they should not become competing policy writers. Coalesce repeated notifications and provide a fair next turn for bots deferred by the limit. Current scheduling, Current defensive hook.

Limit route expansions, candidate evaluation, and transition count independently. Do not assume AzerothCore's in-memory caches survive a Module invocation. Add longer-lived caches only with a concrete invalidation key and measured benefit.

A worked stuck case

A wolf behind a wall matches a held quest. Today, the bot calls fight and can record quest progress even while movement stays still. In the proposal, starting an attack records only acceptance. The runner sees no route advancement, damage, or quest change. After the movement deadline, it tries another approach and then defers that wolf. It selects another eligible wolf or waits for one. This is a predicted sequence to turn into a failing fixture, not a test run performed for this report.

Measure movement against waypoint or route advancement, not just straight-line distance to the destination. A valid detour may first move away from the goal. Keep separate movement, combat, and quest progress clocks so a long route does not look like a broken quest.

6. Build both release goals on the same runner

Autonomous leveling and questing

Build a bounded catalog from LyraCore's imported quest relations, objectives, creature spawns, and loot sources. Admission checks both core eligibility and whether every required objective has an executor. Store the actual ender for each quest. A live creature search answers what can be acted on now; it should not decide whether a quest destination exists in the world.

The first complete loop should accept a quest, retain its objective, travel, kill or collect from the right source, loot, turn in, and continue after death or interruption. Add talk-only chains and supported GameObject use through their real core operations. Exploration, escort, scripted events, transport, and other unsupported objectives remain explicit capabilities to implement, not silent partial support.

Replace the permanent home leash with a current work area and a retained next destination. For an initial Northshire and Elwynn proof, choose a small supported quest catalog. General leveling later needs zone transitions, level-appropriate routes, and an explicit response when a chain or region has no supported continuation. A local 1-to-10 run is an initial proof, not a claim of 1-to-60 coverage.

Human-led companions

Joining a human-led party suspends autonomous travel and opportunistic grouping. The bot follows, assists the party's chosen fight, respects controlled enemies, heals and buffs between fights, and retains its role through death and Transfer. Leaving the party resumes the retained solo objective after rechecking it.

Start with Warrior tank, Priest healer, and Mage damage because the existing package already names those roles and classes. Validate the ability set at each supported level. Make range and available abilities class capabilities; role alone cannot decide whether a bot belongs in melee. Paladin and additional classes follow once the shared loop passes. This is a proposed delivery order, not a requirement to keep those existing kits. Current starter classes.

Companion orders need a small durable contract for follow, stay, assist, and a designated target. The command transport can use the existing chat path. A client addon and new product UI are not required to prove behavior. Do not start a pull solely because an unrelated enemy happens to be nearby.

Automatic training, gear, and supplies

This is part of the requested product, so build a provisioning policy early. On spawn and level-up, reconcile level-appropriate spells, equipment, and supplies through core operations. Check periodically for missing resources, with a bounded target quantity. Keep actual quest credit, XP, loot entitlement, spell costs, and combat Gates authoritative.

Make reconciliation idempotent. Repeating it must not create duplicate equipment or unlimited supplies. Define which items the policy owns, respect equipped upgrades, and avoid deleting quest items. Prefer starter gear at the earned level; do not silently raise a bot's level to match its leader. Record the chosen provisioning profile and revision so a balance change can be explained.

Provisioning reduces the need to build an economy simulation in the first release. Resting, resource use, inventory capacity, and death recovery still need explicit behavior. Automatic supplies should help a bot recover; they should not hide an action loop that never succeeds.

The reference factory provides a practical checklist for skills, spells, talents, gear, bags, food, potions, and reagents. Extract those concerns as separate actions. Its full refresh can also set level, clear inventory and quests, and complete selected quest prerequisites. Those additional effects are outside the automatic training, gear, and supplies you chose. Factory refresh, Prerequisite completion.

Cut over without two active minds

  1. Add the new state in an additive migration. Plan defaults and backfill explicitly. Keep one durable selector that makes exactly one implementation eligible to control a bot.
  2. Run the new pure decision path on recorded facts. It may explain its choices but must issue no gameplay actions. This checks determinism and policy disagreements, not long-term world behavior.
  3. Give a small test cohort to the new runner. Cancel incompatible old movement and retain Character state. Compare independent runs from equivalent fixtures.
  4. Use a freeze mode if a cohort fails. Roll back to the old runner only where its state contract still works; do not call the old behavior safe by default.
  5. After both release suites pass, remove the old control path and obsolete tests. Retire old table storage separately under a reviewed migration plan.
